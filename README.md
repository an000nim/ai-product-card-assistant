# AI-помощник для подготовки товарных описаний

Локальный прототип на Python для B2B-каталога контрольно-измерительных приборов. Принимает JSON товара, обращается к API LLM и возвращает черновик: SEO-заголовок, описание, характеристики, поисковые фразы и commercial-блок. Отсутствующие и спорные данные отмечаются отдельно.

Это реальные результаты Qwen 3 4B Instruct через Ollama. Описания — 904 и 1003 символа с пробелами; заголовки — 37 и 48; по пять запросов. Markdown автоматически построен из JSON, текст вручную не переписывался. Исходный ответ LLM находится в `raw_generation`, программные изменения — в `review`.

## Установка и запуск

Понадобятся Git, Python 3.9+ (проверено на 3.12) и [Ollama](https://ollama.com/).

1. Скачайте проект и перейдите в его папку.

   ```sh
   git clone https://github.com/an000nim/ai-product-card-assistant.git
   cd ai-product-card-assistant
   ```

2. Откройте приложение Ollama. Если Ollama установлена только как консольная команда, запустите `ollama serve` в отдельном терминале. Скачайте модель.

   ```sh
   ollama pull qwen3:4b-instruct
   ```

3. Сгенерируйте карточки. Результаты появятся в папке проекта.

   ```sh
   python3 app.py examples/trm151.json > result-trm151.json
   python3 app.py examples/dts014.json > result-dts014.json
   ```

Для локального запуска достаточно стандартной библиотеки Python. После загрузки модели генерация работает без интернета. На CPU обработка одного товара может занять несколько минут.

Преобразуйте JSON в Markdown этой командой. Чтобы попробовать преобразование сразу после скачивания проекта, используйте готовый файл `examples/results/trm151.json` вместо `result-trm151.json`.

```sh
python3 render_result.py result-trm151.json > result-trm151.md
```

Чтобы при генерации получить сразу Markdown, добавьте `--format markdown`. Полный журнал проверки сохраняется в формате JSON.

## Формат входа

Обязательное поле — непустое `name`. `manufacturer`, `description` и значения `specs` — строки; неизвестную характеристику обозначайте пустой строкой. Неизвестные сведения не нужно угадывать.

```json
{
  "name": "Манометр показывающий DM 02",
  "manufacturer": "Манотомь",
  "specs": {
    "диапазон измерений": "0–1,6 МПа",
    "класс точности": "1,5",
    "присоединение": "G1/2",
    "диаметр корпуса": "100 мм"
  },
  "description": "Прибор предназначен для измерения избыточного давления."
}
```

Это иллюстрация схемы из ТЗ, не третий проверенный прибор. Дополнительно поддерживаются `model`, `profile`, `sources` и `conflicts`; ни одно из них не обязательно для обработки JSON из ТЗ. Подробные примеры находятся в `examples/`.

## Как устроена генерация

1. Проверяются JSON, типы полей, дубли ключей и базовые пропуски по типу прибора.
2. Модель получает исходные факты и инструкцию написать четыре текстовых поля без новых характеристик и назначений.
3. Программа проверяет длину, число запросов, повторы, некоторые неподтверждённые числа, единицы и условия. Та же модель отдельно проверяет утверждения. При замечаниях возможна повторная генерация с конкретной обратной связью.
4. Характеристики копируются из входа, пустые значения помечаются «данных нет». Точные повторы могут удаляться, краткое описание — дополняться дословными входными фактами; любые такие изменения записываются.
5. Возвращается черновик с `missing_fields`, `source_conflicts`, исходными фактами и журналом `review`. В Markdown обязательные части карточки отделены от замечаний.

Промпты `SYSTEM_PROMPT` и `AUDIT_PROMPT` находятся в `app.py`. Модель создаёт содержательный текст, а не только сортирует характеристики. Прямой API Ollama выбран для ограничения памяти: контекст 3072 токена и выгрузка после каждого запроса. Самопроверка той же моделью — дополнительный сигнал, не независимая экспертиза.

## Настройки

| Переменная окружения | По умолчанию | Назначение |
|---|---|---|
| `LLM_BACKEND` | `ollama` | `ollama` либо `openai` для совместимого Chat Completions API |
| `LLM_MODEL` | `qwen3:4b-instruct` | Имя установленной/доступной модели |
| `LLM_MAX_ATTEMPTS` | `2` | От 1 до 3 попыток генерации |
| `OLLAMA_BASE_URL` | `http://127.0.0.1:11434` | Адрес прямого API Ollama |
| `OLLAMA_CONTEXT_SIZE` | `3072` | Контекст 2048–8192 токена |
| `LLM_BASE_URL` | `http://127.0.0.1:11434/v1` | Базовый URL при `LLM_BACKEND=openai` |
| `LLM_API_KEY` | пусто | Ключ внешнего сервиса, если нужен |

Ключей в исходном коде нет. `.env*` исключены в `.gitignore`, но файлы `.env` автоматически не загружаются: задавайте переменные в окружении процесса. Внешний API должен поддерживать `response_format: json_object`. Платные API в проверке проекта не использовались; совместимый режим покрыт тестами с подменой ответа.

## Ошибки и ограничения

Ошибки чтения файла, некорректный JSON, дубли ключей, пустое имя и ошибки API выводятся в stderr с кодом завершения 1. При сбое самопроверки может сохраниться черновик с предупреждением. Код 0 означает получение результата, а не подтверждение всех требований качества: проверяйте `review.automated_issues`, `review.context_warnings` и `missing_fields`.

Если модель недоступна, проверьте, что Ollama запущена и `ollama list` показывает нужную модель; на системах без приложения можно запустить `ollama serve`. Тайм-аут одного запроса — 600 секунд; попытка обычно содержит генерацию и самопроверку. При недостатке памяти закройте ненужные приложения и не запускайте генерации параллельно.

Все результаты — **черновики для проверки человеком**. Автоматические проверки не исключают всех смысловых ошибок, а профили обязательных полей неполны. При недостатке исходных фактов программа может вернуть описание короче 800 символов с предупреждением. Длинные входы могут не помещаться в контекст. Ссылки на источники сохраняются, но программа не скачивает и не проверяет документы автоматически.

В примерах конфликт нагрузки реле оставлен на уточнение, данные серии датчика явно помечены. Перед публикацией проверяются применимость характеристик и паспорт конкретного исполнения. Следующие улучшения: экспертно размеченный набор примеров, проверка утверждений по точным цитатам, расширение профилей и независимая оценка моделей.
