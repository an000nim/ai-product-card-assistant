# Проверка требований ТЗ — 05.11.2026

Основание: «Тестовое задание — AI-помощник для подготовки товарных описаний», переданный PDF. Объём — локальный прототип, не промышленный сервис. Чек-лист составлен по всем разделам ТЗ, включая сдачу.

## Разбор ожиданий работодателя по разделам PDF

### 1. Цель задания

Работодателю нужен небольшой работающий помощник для создания черновиков карточек КИП. Оценивается не объём инфраструктуры, а путь от исходных фактов через API модели до полезного результата. По формулировке «черновик» результат не обязан заменять технического специалиста, однако это не разрешает добавлять выдуманные параметры. Проверен полный путь: два входа → реальные запросы → сохранённые карточки → проверка фактов.

В проекте модель пишет заголовок, описание, поисковые фразы и коммерческий блок. Программа отвечает за сохранность исходных характеристик, оформление, пропуски и предупреждения. Это соответствует роли помощника для контент-менеджера, а не системы подбора или управления прибором.

### 2. Входные данные

Ожидаются название, производитель, краткие характеристики и описание/фрагмент паспорта. Перечень свойств в PDF приведён как пример, а не как обязанность иметь питание и интерфейс у любого прибора. Поэтому обязательные характеристики определяются базовым профилем: для датчика и регулятора они различаются.

Программа принимает схему из PDF. Дополнительные `model`, `profile`, `sources`, `conflicts` необязательны; добавление их в два примера не меняет контракт задания. Пустое название делает запрос непригодным и отклоняется; пропуски производителя, описания и важных характеристик отображаются как недостающие сведения. Два исходных JSON составлены из выбранных записей каталога и дополнены источниками. Это подготовка входных данных, не скрытый поиск модели.

### 3. Поведение сервиса

Все пять действий реализованы: чтение JSON, API-вызов, генерация, копируемый результат, сообщение о пропусках. Формулировка «JSON или простая веб-форма» допускает CLI с JSON. Отдельный HTTP-сервер, браузер и форма не являются обязательным условием.

Для удобства работодателя можно открыть два Markdown-примера прямо в репозитории, без установки модели. Они получены из JSON автоматически. При запуске `app.py` по умолчанию сохраняется подробный JSON; `--format markdown` выдаёт читаемую карточку. `render_result.py` показывает уже сохранённый результат без повторных расходов времени на генерацию.

### 4. Требуемый результат

Карточка состоит из пяти явных частей: SEO-заголовок, SEO-описание, таблица характеристик, поисковые фразы, блок для менеджера. После них идут уточнения и предупреждения, которые не входят в SEO-описание. При подсчёте длины используются именно текстовые значения `title` и `description`, включая пробелы; разметка и диагностический JSON не учитываются.

На обоих примерах соблюдены формальные лимиты: 37/48 символов заголовка, 904/1003 символа описания, по 5 разных запросов. В характеристиках сохранены исходные значения. Коммерческие блоки объясняют задачи и условия применения без придуманной цены, наличия и новых отраслей. Фразы не измерялись по поисковой частотности: ТЗ требует логичных запросов, не SEO-исследования. Смысловые нюансы и применимость сведений серии описаны в REVIEW.

### 5. Технические требования

Реализация на Python, обращения к локальной LLM идут через API Ollama. Ключ локально не требуется; для совместимого внешнего API предусмотрена переменная окружения. В итоговой папке нет файла с ключом, `.env*` исключены.

Проверены неверный синтаксис JSON, неверные типы, пустое имя, отсутствие файла, неправильная кодировка, дубли ключей, недоступность и ошибки API, неверный ответ модели и ограничение длины ответа. При частичном сбое самопроверки приложение сообщает об этом в результате; оно не представляет непроверенный текст как подтверждённый.

Запрет на выдуманные значения обеспечивается ограничениями промпта, копированием характеристик из исходного JSON, проверками и сверкой двух примеров. Технические значения итоговых примеров сопоставлены со входом. Для нагрузки реле сохранён пропуск и конфликт; модель не выбирает спорный знак. Абсолютное отсутствие галлюцинаций на любом будущем входе не доказано: это существенное ограничение LLM-прототипа, а не выполненная универсальная гарантия.

### 6. Комплект сдачи

Подготовлены код, короткий README, два входа и результата, описание промптов и решений, ограничения и направления улучшения. Исходные ответы модели доступны отдельно внутри каждого полного результата, поэтому можно проверить происхождение текстов. Исторические наблюдения находятся в `evaluation/observations`, явно помечены как ранние и не выдаются за актуальные примеры.

Репозиторий: https://github.com/an000nim/ai-product-card-assistant. Архив содержит те же материалы для локального запуска.

### 7. Критерии оценки

Код организован по функциям ввода, API, проверки и обработки; представление вынесено в `render_result.py`. Тесты охватывают ошибки, а не только успешный пример. Промпт явно запрещает домыслы, различает характеристики серии и исполнения, задаёт формат и ограничения. Повторная попытка получает конкретные замечания.

Для менеджера предусмотрена читаемая карточка с отделёнными уточнениями. Для разработчика — полный JSON с исходным ответом, изменениями программы и диагностикой. README начинается с примеров и минимального запуска. Оценка работодателя субъективна; наличие этих материалов подтверждает выполнение проверяемых требований, но не гарантирует балл или приглашение.

### 8. Ограничения объёма

Полноценные CMS, админка, БД, деплой и векторная база не требуются и не добавлены. Описание вакансии упоминает более широкий стек, но он не превращается в дополнительные обязательные условия тестового задания. Docker, RAG и интеграция с Битрикс для данного MVP не нужны.

Ориентир 2–4 часа характеризует ожидаемый небольшой объём, а не задаёт функциональность. Проект остаётся локальным прототипом. Не заявляется, что фактически потраченное на него время уложилось в этот ориентир.

### 9. Формат сдачи

Ссылка на репозиторий внесена в `SUBMISSION.md`; сообщение работодателю отправляется отдельно. Текст сообщения уже описывает реализованное, решения и сложности. Видео и скриншоты необязательны: в PDF они указаны «при необходимости». Сохранённые Markdown и JSON позволяют посмотреть результат без записи экрана.

## Что изменено после повторного прочтения ТЗ

- Добавлены `--format markdown` и отдельный просмотр сохранённого результата; обе карточки доступны для чтения без модели.
- В Markdown сохранены пропуски, конфликты и предупреждения, чтобы красивое оформление не скрывало проблем.
- README перестроен вокруг примеров и запуска; подробное описание перенесено в `docs/IMPLEMENTATION.md`.
- Добавлены тесты сохранности текста и показа предупреждений при преобразовании, экранирования разметки и выбора формата CLI.
- Проверены актуальные JSON, соответствие Markdown исходным значениям и комплект файлов для загрузки.
